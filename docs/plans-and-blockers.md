# Central scope and founder decisions

The company has seven runtime owners: co-founder, product/delivery, engineering, design, growth/customer, independent quality/security, and operations monitor. Product/delivery handles both internal products and client service projects. Seventeen specialist mandates remain capability profiles, rather than separate model agents. Historical task IDs, role labels, reports, preferences and run records remain in Postgres. `team.ts` routes historical capabilities to a current owner without inheriting old integration grants or formatting automation. Retired agent modules are retained as source references, not registered in the running app.

## Propose → discuss → revise → approve → execute

The Plans view is the source of truth for proposed scope, product, priority, measurable outcome, exclusions, assumptions, sources, milestones, owners, predecessor keys, target dates, optional effort estimates and budget uncertainty. The initial portfolio proposals are local records, not automatic launch commitments. Dates must be re-estimated if approval or dependencies slip. An unknown budget stays null; approving a plan does not silently fill it or change the job cap.

`POST /company/plans` creates an immutable revision using `expectedVersion`. The current head is proposed. Plan identity (kind/subject) cannot be swapped during editing. Milestone keys are unique and can depend only on earlier entries, preventing cycles. Goals use their own stable key and cannot overwrite the four established founder mandates. A pending goal does not create runnable milestone tasks. New projects keep their assignments ineligible until their charter and milestones are approved.

The founder can discuss a plan with the co-founder. The comment persists before the AI call. If paused, unconfigured or rate-limited, the UI says the comment is saved and no response is claimed. Retrying a discussion is a new bounded request; there is no hidden unbounded queue. Visible output streams through the existing live ledger. Discussion cannot approve a plan or change its revision. The revision editor supports adding/removing milestones, owner, dates, scope, acceptance and explicit dependency keys.

Approval checks the **exact key, version, SHA-256 payload hash, proposed status and decision reason** under a row lock. Concurrent/stale decisions cannot activate work twice. No model-facing approval tool exists. Goal approval materializes dependency-gated internal artifact assignments atomically. Project approval materializes the approved milestone order and scopes, retaining replaced task history. Revising an active plan pauses new work until reapproval; in-flight scope edits are rejected. Revocation disables new work and exact Discord discussion consent immediately; a read-only run already in progress can finish and remains recorded.

Only independently accepted internal artifacts with no required evidence gap or blocker can be accepted automatically under the displayed founder-approved plan policy. Quality/security assignments are reviewed by the co-founder, avoiding self-review. This artifact workflow has no external execution tools. A milestone report cannot certify recovery, implementation, live payments, deployment, outreach or business success without actual supporting evidence. External actions retain separate exact-content approvals and receipts.

## Actionable blockers

A task blocker inspector shows the actual owner, original capability, cause, task ID, missing evidence and next action. Controls inspect the report, attach a bounded project evidence artifact, check safe recovery, or create a typed founder decision with exact tool IDs, affected agent, setup URL and manual next steps. Setup links must be HTTPS without embedded credentials; opening them does not claim setup completed.

Safe recovery is restricted to an approved, unpaused artifact project with completed prerequisites and an evidence-only failure. New project evidence must postdate the review. A persisted fingerprint prevents retrying the same evidence revision; at most two recoveries per task per day are permitted, sharing the unchanged model limit. The new attempt still requires independent review. Credential, access, billing, provider/configuration and uncertain external-write failures never use this automatic retry path. Unknown cases remain inspectable rather than being marked resolved. Generic access/service/budget/deployment approval records consent; actual configuration and verification remain separate. It never creates a credential, pays, widens Connect tools or deploys.

## Discord discussions

`@Co-Founder status`, `health`, `approvals` and `help` use saved records without model calls. `@Co-Founder engineering: question` (or `agent:`, `product:`, `ui-designer:`, `growth:`, `quality:`, `operations-monitor:`) requests an advisory response from that existing owner.

Before company context can be quoted in a room, the first addressed discussion creates an **exact identity + channel access proposal**. The founder verifies the author and channel audience in Decisions. The only runtime-consumed grant is `discord.advisory:<author-id>:<channel-id>`, alone in an approved access plan. This allows read-only AI discussions for that identity in that channel; all channel readers see the reply. It grants no external tool, goal approval, billing, deployment or further delegation. Revoke the approval in its inspector to disable it. Consent is checked again after generation and before dispatch; a queued private reply is cancelled if consent has been revoked. A send already started under valid consent may finish. Generic tool access requests do not become runtime grants through this mechanism.

Requests persist before execution, expire after 24 hours, have a ten-per-identity daily admission bound for unapproved identities and share the configured hourly job policy; approved discussions have no daily admission cap and the selected local policy has no hourly cap. A paused owner waits. Atomic claims prevent duplicate runs. Interrupted/failed model runs are recorded and not blindly retried; send uncertainty retains the existing reconciliation boundary. Responses are real visible model output, saved in Conversations and sent via the durable receipt ledger. A truncated Discord message links to the complete local record. Ordinary redacted message bodies still require an explicit bot mention; no broader message-content permission is enabled automatically.

## Cost and evidence

Idle monitoring, dependency checks, SSE and status commands do not call an LLM. Main conversation history is bounded to ten messages, with title generation and automatic observational model calls disabled. Relevant plan/prerequisite context replaces sending the full portfolio on each assignment. Routine growth/support uses Luna; complex original capabilities such as account proposals use Sol, as do technical and independent reviews. Explicit per-owner model overrides take precedence. Actual run model and provider-reported usage are retained. Four jobs/hour is a job budget, not a monetary cap; a job may contain a producer and review call. No dollar bill, forecast or product revenue is invented.

The Health view shows observed daily runs and reported usage, including missing-usage counts. This is company OS operational analytics. VocalXI/HelpXI/JewelXI customer analytics are not claimed connected. Their proposed plans require real activation, conversion, retention, error and cost evidence before external growth decisions.

## Founder-delegated internal approvals

When `ASCENDXI_AUTONOMY=internal`, proposed goal plans and internal-project artifact plans with no tool request or positive monetary cap receive an exact, audited automatic decision. Client-project scopes, access, services, budgets and deployments remain founder decisions. Revoked/rejected plans stay stopped. Independent reviewed acceptance is still required. `ASCENDXI_MAX_RUNS_PER_HOUR=0` disables the hourly throttle and approved Discord discussions are no longer subject to the ten-request admission bound; unapproved identities retain that bound. Earlier four-job plan notes are historical assumptions superseded by the founder-selected runtime policy.
